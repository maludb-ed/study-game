## The three ideas

1. **Memory-first** — an application is designed by deciding *what it remembers* before deciding *what it does*. The memory model comes first; features are views over memory. Full explanation: [concepts/memory-first.md](concepts/memory-first.md).
2. **Ask-me-anything** — every SaaS application is secretly a knowledge base. A feature is a pre-packaged answer to a question someone asks the system, and planning is the work of discovering those questions. Full explanation: [concepts/ask-me-anything.md](concepts/ask-me-anything.md).
3. **SaaS Plus+** (pronounced "SaaS Plus Plus") — a dedicated memory-first, ask-me-anything application in which each user or client gets a dedicated database and memory system. Built on sovereign data: clients can build and use AI systems without worrying that the SaaS provider will use their data to train additional models.

Activity memory cannot be backfilled — logging exists from day one.

Based on the search results, here's how Kahoot's scoring formula works:

## Basic Points Calculation

Points are awarded based on the speed of the answer by dividing response time by the question timer. The specific formula is:

Points = floor( (1 − (response_time / question_timer) / 2) × points_possible )

Here's a step-by-step example: If a player responded 2 seconds after a 30-second question timer, that's 2 divided by 30 (0.0667), divided by 2 (0.0333), subtracted from 1 (0.9667), then multiplied by 1000 points possible for 966.7, which rounds to 967 points.

## Maximum Points

Answering straight away can net the maximum 1,000 points per question but waiting until the countdown's dying seconds will yield only half the reward. The formula is not applied when a player responds correctly in less than 0.5 seconds, in which case the player always receives the maximum number of points.

## Answer Streak Bonus

Players that get two correct answers in a row are awarded 100 bonus points for their efforts. However, it's important to note that as of a recent update, bonuses are officially a thing of the past, and while answer streaks still exist, there are no points awarded for them.

Here's the research and the strategy. **TLDR: build a host-paced, server-authoritative quiz game on your standard PHP/HTMX/PostgreSQL stack, with a question bank tagged by exam and domain so every game you play doubles as readiness analytics for the group.** No JavaScript framework or WebSocket infrastructure is needed at study-group scale — short-interval HTMX polling handles the live game loop.

## What makes Kahoot work

The mechanics worth copying are simple and well documented:

- **Two screens.** The host's screen (shared on a projector or screen-share during your group call) shows the question, the answer options, the countdown, and the leaderboard. Each player's own phone or laptop shows only four big colored answer buttons. This split is the core of the game-show feel.
- **Frictionless joining.** The host starts a game and gets a short PIN; players go to one URL, enter the PIN and a nickname, and appear in a live lobby. No accounts required to play.
- **Speed-based scoring.** A correct answer earns up to 1,000 points scaled by speed: roughly `floor((1 − (responseTime/questionTime)/2) × 1000)`, so an instant answer gets ~1,000 and a last-second answer gets ~500. Kahoot historically added a 100-point bonus for answer streaks.
- **The rhythm.** After every question: a bar chart of how the group answered, the correct answer revealed, then a top-5 leaderboard. A podium at the end. The host controls all pacing — nothing advances until they click Next.

That host-paced rhythm is an architectural gift: the game is a simple state machine (`lobby → question → reveal → leaderboard → … → podium`) that only changes when the host advances it or the timer expires.

## Strategy for the app

**Memory first — what the app remembers.** The game is the fun part, but the durable value is the record it builds. Design the schema around the questions your group will ask it:

- *Record memory (PostgreSQL 17):* the **question bank** (each question tagged with exam, domain, difficulty, and source), **games** and their configuration, **players** (a lightweight roster of your study group so results accumulate per person across games), and every **answer** with correctness and response time. That's enough to answer "which CCAR-F domain does the group score worst in?", "who's ready to book their exam?", and "which questions do we keep missing?" — through screens and through the record-memory MCP server, so anyone in the group can point Claude Desktop at it.
- *Activity memory (MaluDB):* log every join, host action, and answer from day one, so "when did we last drill MCP questions?" is answerable later.

**Game engine.** One `games` row holds the authoritative state (phase, current question index, deadline timestamp). The host UI advances the state machine; player screens poll a small game-state endpoint with HTMX every ~1 second and swap in whatever the current phase demands (lobby roster, answer buttons, reveal chart, leaderboard). For a study group of 5–30 people on one server, 1-second polling is trivial load and dramatically simpler than WebSockets — and your stack guidance already names server-sent events as the earned upgrade if polling ever feels laggy. Score answers server-side with the Kahoot formula, using server timestamps so nobody's clock matters.

**Question bank strategy.** This is where your group has an unfair advantage: use Claude to generate the bank. Seed it by domain from the official exam guides, weight game rounds to match the real blueprints (a "CCAR-F night" draws 27% agentic-architecture questions, and so on), and add an editorial screen so members can flag bad questions after each game. The learn-claude plugin's quiz and mock-exam skills cover individual drilling; this app is the group-play layer on top, and the same domain taxonomy should be used in both so results are comparable.

**Build order** (per your plugin's method):

1. Schema + memory design, logging, and the MCP tool surface — first, since activity memory can't be backfilled.
2. Auth + app shell: simple accounts for members (host rights for whoever runs game night); PIN-join stays account-free but lets players claim their roster identity.
3. Vertical slice 1 — question bank: CRUD, tagging, Claude-assisted generation and import.
4. Vertical slice 2 — the game loop: host screen, join flow, play loop, scoring, podium. This is the demo-able milestone.
5. Vertical slice 3 — analytics + AMA agent: domain-level readiness dashboards per player and for the group, plus scenario rounds and team mode as follow-ons.

Deployment is one Ubuntu box behind Apache with a shared URL — everyone joins from wherever they are during the group call.
